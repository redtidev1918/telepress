# TelePress automated releases

TelePress uses a gated automated release process:

```text
Conventional commits
        ↓
Release Please pull request
        ↓ maintainer review and merge
Git tag + GitHub Release
        ↓
Build and metadata verification
        ↓
PyPI Trusted Publishing + GitHub assets
```

版本号、CHANGELOG、标签和发布产物都由自动化维护，但真正发版前仍需维护者合并发布 PR。

## One-time repository setup

### 1. GitHub Actions permissions

In the repository settings, open **Actions → General**:

1. Allow GitHub Actions to create pull requests.
2. Allow workflows to request write permissions. The release workflow narrows
   these permissions per job.

Create a GitHub environment named `pypi`. Requiring a maintainer review for
this environment is recommended for an additional production gate.

For release pull requests to trigger ordinary `pull_request` CI, add a
fine-grained token or GitHub App token as the repository secret
`RELEASE_PLEASE_TOKEN`. Limit it to this repository with read/write access to
contents, issues, and pull requests. The workflow falls back to `GITHUB_TOKEN`
when this secret is absent, but GitHub suppresses follow-up workflow events
created by that built-in token; this can leave a protected release PR without
its required CI check.

### 2. PyPI Trusted Publisher

In the `telepress` project settings on PyPI, add a GitHub trusted publisher:

| Field | Value |
| --- | --- |
| Owner | `redtidev1918` |
| Repository | `telepress` |
| Workflow | `release.yml` |
| Environment | `pypi` |

This enables short-lived OIDC authentication. Do not add a long-lived PyPI API
token to GitHub secrets.

If the PyPI project does not exist yet, create a pending publisher with the
same values before the first release.

## Normal release flow

1. Merge pull requests into `master` using Conventional Commit titles.
2. The `Release` workflow creates or updates a release pull request.
3. Review the proposed version and `CHANGELOG.md` in that pull request.
4. Merge the release pull request.
5. Release Please creates the `vX.Y.Z` tag and GitHub Release.
6. The same workflow checks out the tagged revision, builds the wheel and
   source distribution, validates metadata and the installed version, then
   publishes through PyPI Trusted Publishing.
7. After PyPI succeeds, the wheel and source archive are attached to the
   GitHub Release.

No local version bump, tag, or `twine upload` command is needed.

## Version policy

Release Please follows Semantic Versioning based on commit messages:

| Commit | Version effect |
| --- | --- |
| `fix:` | Patch, for example `0.3.5 → 0.3.6` |
| `feat:` | Minor, for example `0.3.5 → 0.4.0` |
| `feat!:` / `BREAKING CHANGE:` | Minor before 1.0 (`0.3.5 → 0.4.0`), major after 1.0 |
| `docs:`, `test:`, `chore:` | No release by itself |

The package version has one source of truth:
`src/telepress/version.py`. `pyproject.toml` reads it dynamically.

To request an exact exceptional version, include this footer in a conventional
commit and review the generated release PR carefully:

```text
Release-As: 0.4.0
```

## Failure recovery

- If CI fails before the release PR is merged, fix the release PR or the
  underlying change and wait for it to update.
- If the release build or PyPI job fails after the GitHub Release is created,
  fix the external configuration when necessary and rerun the failed jobs.
- PyPI versions are immutable. Never delete and reuse a published version;
  prepare a new patch release instead.
- Do not manually move or overwrite release tags generated by Release Please.

The `workflow_dispatch` trigger can rerun release reconciliation manually, but
it does not bypass version calculation or the release pull-request gate.

## Automation files

- `.github/workflows/ci.yml`: Python 3.10–3.14 tests and package build
- `.github/workflows/release.yml`: release PR, build, PyPI publish, assets
- `release-please-config.json`: version and changelog policy
- `.release-please-manifest.json`: last released version
- `.github/dependabot.yml`: weekly Python and GitHub Actions updates
